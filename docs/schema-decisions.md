# Схема БД: принятые решения и допущения

Черновик для разделов README «Схема БД» и «Допущения и упрощения».

## Принятые решения

### Деньги хранятся целым числом копеек

Все суммы — `BIGINT` в минорных единицах (`price_minor`, `total_minor`). Никаких `NUMERIC`
и тем более `float`. Дробные типы дают ошибки округления, которые всплывают при суммировании
корзины. Валюта в MVP одна, поле для неё не заводим, но переименовать колонки при
необходимости дешевле, чем чинить копейки.

### Статусы — `TEXT` с `CHECK`, а не тип `ENUM`

Нативный `ENUM` в PostgreSQL неудобно менять: добавление значения требует отдельной
миграции, удаление невозможно без пересоздания типа. `TEXT` с ограничением даёт ту же
защиту от мусора, но меняется обычным `ALTER TABLE`.

### Название и цена копируются в `order_items`

`name_snapshot` и `unit_price_minor` дублируют данные из `menu_items`. Это сделано намеренно:
заведение может переименовать блюдо или изменить цену, и уже оформленный заказ не должен
меняться задним числом. Ссылка на `menu_item_id` при этом сохраняется — она нужна для
аналитики и для связи с остатками.

### Стоп-лист и остаток — два разных механизма

`is_available = false` означает «заведение выключило позицию руками». `stock_qty` — жёсткий
счётчик, который уменьшается при каждом заказе. `stock_qty = NULL` означает «количество
не ограничено», что типично для блюд, готовящихся под заказ.

Разделение нужно, потому что причины недоступности разные и сообщения пользователю тоже
должны быть разными: «сегодня не готовим» и «осталась одна порция вместо трёх» — не одно
и то же.

### Пересечение акций запрещено ограничением базы

На `rescue_offers` висит exclusion constraint:

```sql
EXCLUDE USING gist (
    menu_item_id WITH =,
    tstzrange(starts_at, ends_at) WITH &&
) WHERE (cancelled_at IS NULL)
```

Читается так: не может существовать двух неотменённых строк, у которых совпадает позиция
меню и при этом пересекаются временные окна. Требует расширения `btree_gist`, потому что
GiST-индексу нужно уметь проверять обычное равенство по `uuid` наряду с пересечением
диапазона.

Проверка в коде здесь не годится: между «проверил, что пересечений нет» и «вставил» проходит
время, и два одновременных запроса пройдут проверку оба. База такого не допустит.

### `menu_version` — счётчик изменений меню

Увеличивается на единицу в той же транзакции, которая меняет меню, категории, цены,
стоп-лист, остатки или акции. Используется как значение `ETag`, чтобы отвечать
`304 Not Modified` на неизменившееся меню, и пригодится для инвалидации кэша, когда он
появится.

### `source` и `external_id` — связь с источником данных

Это прямой ответ на требование ТЗ «подумайте, как связать данные в вашей системе
с источниками данных». Позиция, импортированная из системы заведения, хранит идентификатор,
под которым она известна на той стороне. Уникальный индекс `(venue_id, external_id)` делает
повторную синхронизацию меню идемпотентной: повторная загрузка обновляет существующие
позиции, а не плодит дубли.

### `outbox_events` без внешних ключей

Единственная таблица без связей. Событие самодостаточно: в нём лежит готовый JSON, который
уйдёт получателю. Если заказ когда-нибудь удалят, событие не должно исчезнуть или заблокировать
удаление. Плюс это заранее развязывает таблицу на случай, если outbox переедет в отдельный
сервис со своей базой.

### Частичные индексы под конкретные запросы

Три индекса покрывают не всю таблицу, а её рабочий срез:

- `outbox_events_due_idx` — только `status = 'pending'`, потому что воркер смотрит только туда.
- `rescue_offers_active_idx` — только живые непроданные акции, для подборки.
- `menu_items_venue_external_uq` — только строки с непустым `external_id`.

Частичный индекс меньше, быстрее обновляется и точнее отражает намерение.

## Допущения и упрощения

| Упрощение | Обоснование |
|---|---|
| Расписание не поддерживает смены через полночь (`closes_at > opens_at`) | Поддержка ночных смен требует хранить интервал иначе и усложняет проверку «открыто ли сейчас». К предмету оценки отношения не имеет |
| Один интервал работы на день недели | Обеденных перерывов у заведений в MVP нет |
| Одна валюта, поле не заводится | Мультивалютность вне scope |
| Телефон и адрес — свободный текст, без валидации формата и без геокодирования | Зоны доставки вынесены в необязательные сценарии |
| Корзина живёт вечно, TTL не чистится | Для MVP не критично; при росте добавляется фоновая уборка по `updated_at` |
| `idempotency_keys.expires_at` есть, но фоновой очистки нет | Достаточно индекса; уборку добавить одной командой позже |
| Скидка по акции только в процентах | Фиксированная сумма потребовала бы второго поля и ветвления в расчёте |
| Одна акция на позицию в один момент времени | Наложение скидок — отдельная продуктовая задача |
| Оплата не моделируется, считается оплатой при получении | Платежи вне scope по условию |
| Клиент идентифицируется UUID из заголовка, без подтверждения | По условию ТЗ авторизация не требуется. Это означает, что чужой заказ можно посмотреть, зная его идентификатор — осознанное следствие требования, а не упущение |
| В ответах API деньги — объект `Money {amountMinor, currency}`, а в телах запросов — просто `priceMinor`/`minOrderAmountMinor` без `currency` | Валюта в MVP одна, клиент не может её выбрать. Требовать поле `currency` в каждом запросе было бы кодом «на вырост»; в ответах оно остаётся ради формата из раздела 7.1 и будущей мультивалютности |
| В `ErrorCode` обоих API добавлены коды сверх таблицы 5.2: `VALIDATION_ERROR`, `NOT_FOUND`, `INTERNAL_ERROR` (+ `UNAUTHORIZED` в партнёрском), `CART_VENUE_MISMATCH`, `CART_EMPTY` | Первые три — стандартные случаи, без которых REST-контракт неполный, ТЗ их не перечисляет только потому, что это не бизнес-конфликт. `CART_VENUE_MISMATCH` и `CART_EMPTY` описаны в тексте сценариев (5.1.3, оформление заказа), но без выделенного кода в таблице — код добавлен по аналогии с остальными |
| `PUT /partner/menu` матчит категории по `name`, а `POST /menu/items` требует уже существующую категорию | У `menu_categories` в схеме БД нет `external_id` (только у `menu_items`), поэтому категория не может синхронизироваться по внешнему идентификатору. Следствие: новую категорию можно завести только через полную синхронизацию, точечная ручка добавления категории не предусмотрена |
| `webhookSecret` генерируется сервером при первой установке или смене `webhookUrl` в `PATCH /partner/venue` и возвращается один раз в теле ответа | ТЗ не описывает способ выдачи секрета для HMAC-подписи вебхука. Решение по аналогии с выдачей API-ключей партнёрам: показать значение один раз, дальше — только использовать |
| Самовывоз, зона доставки вне зоны и формат исходящего вебхука не описаны в OpenAPI-спеках (этап 2) | Первые два помечены в ТЗ как «если останется время» и добавляются в спеку только если до них дойдёт очередь. Вебхук — контракт между платформой и сервисом-заведением, а не часть `public.yaml`/`partner.yaml`; будет описан в README (раздел «События и брокер сообщений») |
| Каждый API-ключ однозначно определяет одно заведение | Сделано через модель «1 партнёр = 1 заведение», что проще и не требует лишнего поля в схеме (`partner_api_keys` ссылается на `partner_id`, а не на `venue_id`). Раздел 5.3 ТЗ прямо говорит «ключ определяет заведение» — при партнёре с несколькими заведениями это было бы неоднозначно, поэтому демо-сиды (`cmd/seed`) заводят отдельного партнёра на каждое заведение |

## Что проверить при запуске

- `goose up` и `goose down` проходят полностью, без остатков в схеме.
- Расширение `btree_gist` создаётся до таблицы `rescue_offers`, иначе миграция упадёт.
- `gen_random_uuid()` доступна без расширений — она в ядре начиная с PostgreSQL 13.
  На более старых версиях понадобится `pgcrypto`.
